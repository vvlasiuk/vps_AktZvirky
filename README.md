# vps_AktZvirky

Окремий спеціалізований Telegram-бот для формування **акту звірки** з 1С.
Один процес, без RabbitMQ — швидко розгортається у клієнта (один `.env`,
жодного окремого брокера/сервера БД).

## Чому так (контекст рішення)

Цей проект — виділений з `vps_dispatcher` (плагін `demo_bot`) + `vps_output_msg_1C`
+ `vps_input_msg_telegram`/`vps_output_msg_telegram`. Там ці 4 сервіси
з'єднані через RabbitMQ, бо це виправдано для мульти-ботового диспетчера
на різних машинах. Тут — один вузькоспеціалізований бот на одному сервері,
тому весь той транспорт замінено на прямі виклики в одному процесі:

- Telegram (long polling + відправка) — `python-telegram-bot`, в одному місці замість двох сервісів.
- 1С (COM) — окремий потік з єдиною сесією (COM вимагає STA-апартамент), замість окремого процесу-моста.
- Транспорт між ними — не RabbitMQ, а прямі виклики + thread-safe черга в пам'яті.

Що навмисно **не** перенесено: WorkflowState/LangGraph з `vps_dispatcher`
(тут немає багатокрокових діалогів — кожен клік самодостатній) і
токени/контекст з `vps_api` (акт звірки не використовує підтвердження
через HTML-кнопки).

Що **залишено**: плагінова структура (`matches()` / `run()` /
`on_onec_result()`, реєстр плагінів) — за зразком `vps_dispatcher`, щоб
можна було дописувати нові плагіни, не переробляючи ядро (`main.py`,
`telegram_app.py`, `onec_worker.py`).

## Архітектура

```
Telegram (ручний long-polling, TelegramGateway на raw HTTP, offset на диску)
        │  asyncio.gather() — усі update'и з однієї пачки getUpdates паралельно
        ▼
 PluginRegistry.find_for_event()  →  плагін (matches/run)
        │                                   │
        │ негайна відповідь                  │ OneCSubmission (опційно)
        ▼                                   ▼
  gateway.send_message/document   OneCWorker.submit() (thread-safe queue)
        │                                   │
        │                          окремий потік, одна COM-сесія (STA)
        │                          CreateTask (миттєво) → у циклі опитує
        │                          StatusTask для ВСІХ задач у польоті
        │                          (не чекає по черзі — короткий non-blocking
        │                          виклик на кожну, і йде далі)
        │                                   │
        │                          run_coroutine_threadsafe(deliver_onec_result)
        │                                   │
        ▼                                   ▼
  👀-реакція / answerCallbackQuery   gateway.send_message/document
  (лише після успішної обробки)
```

Після успішної обробки update'у (а не до) — 👀-реакція на message-подіях,
`answerCallbackQuery` на callback_query. Це той самий контракт, що в
`vps_input_msg_telegram`.

Ключове технічне рішення: `CreateTask` у 1С повертається майже миттєво
(1С виконує звірку асинхронно на своєму боці), тому обробник Telegram
ніколи не блокується довгим очікуванням — користувач одразу отримує
"⏳ Формую акт звірки…", а результат приходить окремим повідомленням,
коли 1С завершить.

### Чому не потрібна повноцінна БД

Акт звірки — операція без діалогового стану (кожен клік меню
самодостатній), тому `WorkflowState` (як у `vps_dispatcher`) тут не
потрібен. Єдине справжнє вікно ризику — процес може впасти саме тоді,
коли задача вже створена в 1С, але результат ще не доставлений. Для
цього є **одна SQLite-таблиця** `pending_tasks` (`storage/state.sqlite3`,
`src/state_store.py`): запис перед відправкою в 1С, оновлення при
отриманні `task_id`, видалення при доставці. При старті сервіс підхоплює
незавершені записи і продовжує опитування (або повторно створює задачу,
якщо впав до отримання `task_id` — це безпечно, бо звірка ідемпотентна:
повторне формування нешкідливе). SQLite обраний навмисно — не потребує
окремого сервера БД, що важливо для швидкого розгортання у клієнта.

### Навантаження від багатьох користувачів

- Усі update'и, отримані в одному виклику `getUpdates`, обробляються
  паралельно (`asyncio.gather` у `TelegramApp.run_forever()`), а не по
  черзі — один повільний плагін не блокує інших користувачів. `offset`
  просувається лише до першого update'у в пачці, що впав (детальніше —
  у docstring `TelegramApp`), тому провал одного не губить решту.
- Усі звернення до 1С ідуть через один потік з однією COM-сесією
  (`OneCWorker`, STA-апартамент вимагає одного потоку — як і в проді,
  `vps_output_msg_1C`). Важливо: цей потік **не чекає по черзі**
  завершення кожної задачі — `CreateTask` повертається майже миттєво
  (1С сама виконує звірку асинхронно, у власному потоці на своєму боці),
  а `_poll_in_flight()` у циклі робить короткий non-blocking `StatusTask`
  для КОЖНОЇ задачі, що вже в польоті, і йде далі — не чекаючи, поки
  конкретна задача завершиться. Тобто серіалізується (через одну
  COM-сесію) лише сума коротких викликів диспетчеризації
  (`CreateTask`/`StatusTask`, мілісекунди кожен), а не сама тривалість
  формування акту звірки — вона йде паралельно на боці 1С. Для 100
  користувачів це додає затримку порядку мілісекунд на постановку задачі
  плюс до `POLL_INTERVAL_SEC` (типово 2с) на виявлення готовності —
  не час самої звірки.
- Реальне жорстке обмеження — швидкість самих COM-викликів
  (`CreateTask`/`StatusTask`) до конкретного сервера 1С під навантаженням;
  це залежить від інсталяції і вимірюється окремо. Якщо колись
  виявиться замалим — код структурно готовий до кількох паралельних
  `OneCWorker` (кількох COM-сесій), бо `onec_worker.py` не залежить від
  глобального стану. Навмисно не зроблено одразу, щоб не ускладнювати
  проект без підтвердженої потреби.

## Розгортання

1. `setup.bat` — створить `.venv` і встановить залежності.
2. Скопіюйте `.env.example` → `.env`, заповніть `TELEGRAM_TOKEN` і реквізити 1С.
3. Скопіюйте `run.bat.example` → `run.bat`.
4. `run.bat`.

## Конфігурація

Див. `.env.example` — усі параметри з коментарями. Основне:

- `TELEGRAM_TOKEN` — токен бота.
- `TELEGRAM_OFFSET_FILE` — файл, де зберігається offset `getUpdates` (просувається лише після успішної обробки).
- `COMMANDS_FILE` — файл команд бота (`setMyCommands` при старті).
- `ONEC_FILE_PATH` — для файлової бази 1С; якщо порожньо — використовується серверне підключення (`ONEC_SERVER`/`ONEC_REF`).
- `POLL_INTERVAL_SEC` — як часто перепитувати `StatusTask` для задач, що ще не готові.
- `TASK_TIMEOUT_SEC` — скільки чекати відповіді від 1С, перш ніж повідомити користувачу про таймаут.

## Команда 1С

Бот відправляє в 1С команду `AKTZVIRKY` з параметрами `chat_id`,
`date_start`, `date_end` (формат `ДД.ММ.РРРР`) і очікує у відповідь
команду `AKTZVIRKY_COMPLETED` з `DATA.text` та, опційно,
`DATA.file: [{file_name, file_base64}]` — той самий контракт, що вже
реалізований у 1С для існуючого плагіна `demo_bot`.

## Додавання нового плагіна

1. Створити `src/plugins/<назва>/plugin.py`, успадкувати `MessagePlugin`
   (`src/plugins/base.py`), реалізувати `matches()` і `run()`, за потреби
   `on_onec_result()`.
2. Зареєструвати екземпляр у `PluginRegistry(...)` в `main.py`.
3. Якщо кілька плагінів можуть відповісти на одне повідомлення — розмежувати
   через `score` у `MatchDecision` (виграє найвищий).

## Тести

`tests/` — юніт- і сценарні тести чистої логіки (розрахунок періодів,
маршрутизація плагінів, SQLite-персистентність, поведінка `OneCWorker`
під навантаженням з підміненим 1С-клієнтом). Це саме ті сценарії, які
можна перевірити без живого Telegram-бота і без 1С:

- `/start`, меню, вибір періоду (поточний/попередній місяць, з початку року, довільний період через веб-апп — точний контракт `command_name`/`command_params`, а не голий `{"date_start":...}`);
- відповідь 1С з файлом / без файлу / з помилкою / з таймаутом;
- захист від path traversal в імені файлу з 1С;
- розбір Telegram-апдейтів (`TelegramGateway.extract_event`): текст, callback_query, web_app_data — без мережі;
- `TelegramApp`: 👀-реакція лише після успіху, `answerCallbackQuery` для callback_query, offset просувається лише до першого провалу в пачці;
- **навантаження**: 40–50 "користувачів" одночасно проходять повний цикл — перевіряється, що жодна відповідь не губиться і не переплутується між чатами;
- **відновлення після падіння процесу**: задача, що вже отримала `task_id` в 1С, підхоплюється і доопитується після рестарту сервісу, а не губиться.

Запуск:

```bash
pip install pytest
pytest tests/ -v
```

`onec_client.py` (реальний COM-виклик) і фактичний прийом/відправка через
Telegram API тестами не покриті — вони потребують живого Windows-сервера
з 1С і реального бота; ці частини варто перевірити вручну після першого
розгортання за сценаріями вище (натиснути кожну кнопку меню, дочекатись
відповіді, перевірити файл).

## Логування

`logs/service.log` (ротація), рівень — `LOG_LEVEL` в `.env`. При втраті
COM-сесії до 1С воркер логує помилку і намагається перепідключитись з
інтервалом `ONEC_RECONNECT_INTERVAL_SEC`.
